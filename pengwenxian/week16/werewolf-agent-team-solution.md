# AI 狼人杀 Agent Team 方案设计

## 1. 项目背景

本项目目标是基于多 Agent 协作框架，构建一个能够自主完成信息不对称博弈的狼人杀 Agent Team 系统。系统中的每个 Agent 扮演一个独立角色，如狼人、预言家、女巫、猎人、平民等，在严格信息隔离的约束下进行推理、发言、投票和技能决策。

系统不仅需要能够完整驱动一局狼人杀游戏，还需要提供结构化日志、全程可观测能力、赛后复盘归因、批量评测与排行榜等配套能力。根据当前目标，优先方向选择为：

- 先完成可运行的对局引擎
- 明确规则与角色能力定义
- 搭建多角色 Agent 决策运行时
- 补齐结构化日志与复盘归因系统
- 在此基础上建设评测体系与 Leaderboard

## 2. 项目目标

### 2.1 核心目标

- 构建一个完整的狼人杀对局引擎
- 支持多个独立 Agent 在同一对局中博弈
- 保证不同角色之间的信息严格隔离
- 支持夜晚行动、白天发言、投票、技能结算与胜负判定
- 输出结构化日志，支持回放与复盘
- 支持批量对局评测，形成多维度指标与排行榜

### 2.2 扩展目标

- 支持纯 AI 对战
- 支持人机混战
- 支持前端观战 UI
- 支持不同模型、不同 Prompt、不同 Agent 策略版本横向对比

## 3. 第一版范围定义

为了尽快形成闭环，第一版推荐使用 9 人标准局作为 MVP。

### 3.1 推荐局型

- 狼人 x3
- 预言家 x1
- 女巫 x1
- 猎人 x1
- 平民 x3

### 3.2 第一版支持能力

- 初始化对局与角色分配
- 夜晚阶段行动
- 白天阶段发言与投票
- 放逐、死亡与技能结算
- 胜负判定
- 结构化日志记录
- 单局回放
- 批量多局评测
- 基础复盘归因分析

### 3.3 暂缓功能

- 警长竞选与警徽流
- 更复杂角色，如守卫、骑士、白痴、禁言长老
- 多规则局型切换
- 高级前端交互与复杂动画

## 4. 设计原则

### 4.1 规则优先

游戏规则必须由代码引擎强制约束，而不是依赖大模型自行遵守。所有角色行动、可见信息、技能触发、回合推进都由规则引擎决定。

### 4.2 信息隔离

每个 Agent 只能获取其当前身份允许知道的信息。狼人可以知道队友身份，预言家只能看到自己的验人结果，女巫只能知道与自己技能相关的夜晚信息。

### 4.3 事件驱动

对局过程统一由事件驱动，所有阶段推进、玩家行动、引擎裁决、状态变化都以事件形式记录，便于回放和复盘。

### 4.4 可插拔 Agent

角色决策能力与底层模型解耦，支持：

- LLM Agent
- Scripted Agent
- Human Agent

### 4.5 全程可观测

对局中每一个关键步骤都要有结构化记录，既方便调试，也为后续评测与归因提供数据基础。

## 5. 总体架构

系统建议拆分为以下五层：

1. 规则与引擎层
2. Agent 运行时层
3. 信息过滤与日志层
4. 评测与复盘层
5. 前端观战与交互层

## 6. 模块拆分

### 6.1 对局引擎层

负责驱动整局游戏，是系统的核心权威状态来源。

建议模块：

- `game_engine.py`：主对局驱动器
- `phase_manager.py`：阶段推进
- `resolver.py`：技能与死亡结算
- `win_checker.py`：胜负裁定

职责：

- 初始化游戏
- 推进夜晚与白天流程
- 组织角色行动
- 校验行动合法性
- 更新全局状态
- 判定是否结束

### 6.2 规则定义层

负责局型规则、角色能力和行动窗口的配置化定义。

建议模块：

- `base_rule.py`
- `werewolf_9p.py`
- `role_definitions.py`

职责：

- 定义角色与阵营
- 定义技能可用时机
- 定义可行动作集合
- 定义特殊技能结算逻辑
- 定义胜利条件

### 6.3 Agent 运行时层

负责对接每个玩家的 Agent，使其在私有可见信息下做出行为。

建议模块：

- `base_agent.py`
- `llm_agent.py`
- `scripted_agent.py`
- `human_agent.py`

职责：

- 为不同类型 Agent 提供统一接口
- 接收裁剪后的观察输入
- 输出结构化行动结果
- 在输出非法时进行重试或降级

### 6.4 信息过滤层

负责把全局状态裁剪为每个玩家可以看到的局部视图。

建议模块：

- `visibility.py`
- `session.py`
- `action_schema.py`

职责：

- 从全局状态生成 `player_view`
- 严格控制私有信息边界
- 为不同角色构造行动输入
- 统一输出格式

### 6.5 日志与回放层

负责结构化记录对局中所有关键事件。

建议模块：

- `logger.py`
- `replay_builder.py`

职责：

- 记录公共事件
- 记录私有事件
- 记录 Agent 决策摘要
- 生成 Replay 数据
- 支持复盘报告所需的数据聚合

### 6.6 评测与归因层

负责多局统计分析、结果评测、过程评测和复盘归因。

建议模块：

- `batch_runner.py`
- `metrics.py`
- `attribution.py`
- `leaderboard.py`

职责：

- 批量跑局
- 计算多种指标
- 生成复盘报告
- 维护不同 Agent 版本排行榜

### 6.7 前端观战层

作为加分项在第二阶段建设，用于直观展示对局过程。

职责：

- 展示玩家席位与状态
- 展示回合时间线
- 展示发言、投票、死讯
- 提供多视角切换
- 展示复盘与归因结果

## 8. 对局引擎设计

### 8.1 核心状态对象

建议建立统一的 `GameState` 作为权威状态。

关键字段建议包括：

- `game_id`
- `day`
- `phase`
- `players`
- `alive_player_ids`
- `dead_player_ids`
- `public_history`
- `private_histories`
- `night_actions`
- `vote_records`
- `winner`
- `is_game_over`

### 8.2 阶段状态机

推荐使用显式状态机推进流程。

建议阶段：

1. `init`
2. `night`
3. `night_resolution`
4. `day_announce`
5. `speech`
6. `vote`
7. `exile_resolution`
8. `last_words`
9. `game_over`

### 8.3 一轮对局流程

```text
初始化身份
-> 夜晚开始
-> 狼人协同刀人
-> 预言家验人
-> 女巫决定是否救人/毒人
-> 夜晚统一结算
-> 白天公布昨夜死讯
-> 存活玩家依次发言
-> 所有人投票
-> 结算放逐结果
-> 触发遗言/猎人开枪等效果
-> 胜负检查
-> 进入下一轮
```

### 8.4 结算器设计

`Resolver` 需要统一处理多技能冲突。

第一版需要处理的重点：

- 狼人击杀目标
- 女巫解药是否抵消死亡
- 女巫毒药附加死亡
- 猎人死亡是否可以开枪
- 多人同时死亡的结算顺序

### 8.5 胜负判定

建议封装 `WinChecker`。

标准判定可包括：

- 所有狼人出局则好人阵营胜利
- 所有神职死亡且平民无翻盘能力则狼人胜利
- 所有平民死亡则狼人胜利

若后续加入新角色，再扩展特殊判定。

## 9. 规则表达设计

不要把规则写死在 Prompt 中，而应通过代码配置化表达。

### 9.1 角色定义建议

每个角色建议包含以下字段：

- `name`
- `camp`
- `can_speak`
- `night_actions`
- `day_actions`
- `passive_skills`
- `visibility_rules`
- `win_conditions`

### 9.2 规则接口建议

```python
class BaseRule:
    def get_available_actions(self, player_id, phase, state):
        ...

    def validate_action(self, action, state):
        ...

    def resolve_phase(self, state, actions):
        ...

    def check_game_over(self, state):
        ...
```

### 9.3 第一版角色说明

#### 狼人

- 夜晚可参与击杀一名玩家
- 知晓所有狼人身份
- 白天需伪装自己，隐藏狼人阵营
- 目标是淘汰所有神职或所有平民

#### 预言家

- 每晚可查验一名玩家阵营
- 只能知道自己的查验结果
- 白天可选择公开或隐藏身份信息

#### 女巫

- 拥有一瓶解药和一瓶毒药
- 解药通常只能使用一次
- 毒药通常只能使用一次
- 可根据信息判断是否救人或毒人

#### 猎人

- 被放逐或死亡时可以开枪带走一人
- 行动时机由规则控制

#### 平民

- 无主动技能
- 依靠发言、投票和归纳推理参与博弈

## 10. Agent 设计

### 10.1 Agent 基本组成

每个 Agent 建议由以下部分组成：

- 角色设定 Prompt
- 当前私有观察输入
- 短期记忆
- 决策策略
- 输出解析器

### 10.2 统一接口建议

```python
class BaseAgent:
    def observe(self, observation):
        ...

    def decide_action(self, action_schema):
        ...

    def speak(self, context):
        ...

    def summarize_memory(self):
        ...
```

### 10.3 Agent 类型建议

#### LLM Agent

用于真实博弈决策，适合夜晚行动、白天发言、投票与归纳推理。

#### Scripted Agent

用于开发调试和基线对照，可以写固定策略或启发式策略，避免开发早期完全依赖大模型稳定性。

#### Human Agent

用于人机混战，用户可以在指定阶段输入自己的行动或发言。

### 10.4 Agent 输出格式建议

```json
{
  "action_type": "vote",
  "target_id": "player_4",
  "reasoning_summary": "4号玩家发言前后不一致，且在关键轮次主动带偏视角",
  "confidence": 0.78,
  "public_message": "我今天投4号，他的逻辑问题最大。"
}
```

### 10.5 输出约束建议

为提高系统稳定性，建议：

- 强制 JSON 格式输出
- 严格定义字段 schema
- 对输出非法内容做重试
- 在连续失败时降级为默认安全动作

## 11. 信息隔离设计

这是本项目最关键的系统约束之一。

### 11.1 核心原则

- 引擎持有唯一全局真相状态
- Agent 不直接访问全局状态
- 所有 Agent 输入都来自裁剪后的 `player_view`

### 11.2 视图划分

#### 全局视图

仅供引擎和上帝视角观战使用，包含所有玩家真实身份和完整行动记录。

#### 公共视图

供所有玩家共享，包含公开发言、投票结果、公开死亡信息等。

#### 私有视图

每个角色独有。

示例：

- 狼人可见其他狼人身份与狼队讨论信息
- 预言家可见自己的查验结果
- 女巫可见与药剂使用相关的夜晚信息

### 11.3 建议实现方式

建立统一函数：

```python
def build_player_view(game_state, player_id):
    ...
```

该函数负责根据角色、存活状态、当前阶段、规则约束，对全局状态进行裁剪。

## 12. 狼人协作机制

为体现多 Agent 团队协作，狼人阵营建议设计为一个小型协作团队，而不是简单单体决策。

### 12.1 推荐机制

夜晚阶段：

1. 每只狼人先独立提名一个击杀目标
2. 每只狼人给出自己的理由摘要
3. 狼队内部汇总讨论
4. 使用简单投票或协调器产出最终刀口

### 12.2 协作价值

- 更符合多 Agent 协作主题
- 更适合做过程评测
- 更容易分析狼队协同质量

## 13. 白天发言与博弈设计

白天发言是狼人杀博弈的关键，应显式区分内部推理与公开表达。

### 13.1 建议双层输出

- `private_reasoning_summary`：供日志与复盘使用
- `public_message`：供白天发言使用

### 13.2 发言约束建议

- 限制字数
- 限制一轮发言次数
- 明确发言阶段顺序
- 统一输出风格与长度

### 13.3 好处

- 降低大模型过度发散
- 降低越界泄漏概率
- 提高复盘时的分析价值

## 14. 日志与可观测性设计

结构化日志是后续回放、复盘、评测的基础设施，必须从第一版开始设计。

### 14.1 日志分类

#### 引擎日志

记录阶段推进、规则校验、状态更新、异常处理。

#### Agent 日志

记录 Agent 的可见输入、决策输出、理由摘要、失败重试。

#### 公共日志

记录发言、投票、死讯、放逐、胜负结果等公共信息。

### 14.2 事件字段建议

- `game_id`
- `round`
- `phase`
- `event_type`
- `actor_id`
- `visibility_scope`
- `payload`
- `timestamp`

### 14.3 示例结构

```json
{
  "game_id": "g_001",
  "round": 2,
  "phase": "speech",
  "event_type": "agent_decision",
  "actor_id": "player_6",
  "visibility_scope": "private",
  "payload": {
    "role": "seer",
    "chosen_action": "speak",
    "reasoning_summary": "2号玩家持续保护4号，但没有形成闭环逻辑",
    "suspicion": {
      "player_2": 0.81,
      "player_4": 0.34
    }
  },
  "timestamp": "2026-05-28T10:01:23Z"
}
```

## 15. 复盘归因系统设计

当前优先的进阶方向为 `评测 + 复盘`，建议拆成三层能力。

### 15.1 结果评测

回答“赢没赢”和“谁更强”的问题。

指标建议：

- 总体胜率
- 阵营胜率
- 角色胜率
- 平均回合数
- 单局平均耗时
- 平均成本

### 15.2 过程评测

回答“打得怎么样”的问题。

指标建议：

- 发言一致性
- 投票合理性
- 查验信息利用率
- 女巫救毒收益
- 狼人协作效率
- 关键轮次身份判断准确率
- 带票成功率

### 15.3 归因分析

回答“为什么赢”和“为什么输”的问题。

归因维度建议：

- 关键决策点归因
- 错误归因
- 协作质量归因
- 信息利用归因
- 模型短板归因

### 15.4 单局复盘输出建议

- 对局摘要
- 关键时间线
- 转折点分析
- 阵营视角分析
- 角色视角分析
- 错误行动 Top N
- 可替代行动建议

## 16. Leaderboard 设计

排行榜不建议只看总胜率，推荐多维展示。

建议维度：

- 总胜率
- 狼人胜率

- 角色专项胜率
- 平均局时
- 平均成本
- 发言质量分

支持比较对象：

- 不同模型
- 不同 Prompt 版本
- 不同策略版本
- 不同规则局型

## 18. 技术选型建议

### 18.1 后端

推荐：

- Python
- FastAPI

原因：

- 适合状态机和规则表达
- 适合调用大模型
- 适合脚本化评测
- 生态成熟，开发效率高

### 18.2 前端

推荐：

- React
- TypeScript
- Vite

可选：

- Zustand 用于状态管理
- Ant Design 或 shadcn/ui 用于快速搭建界面

建议使用 WebSocket 推送对局进展与观战信息。

### 19.2 Action

class Action:

## 21. MVP 验收标准

第一版建议以以下标准作为验收节点：

- 能稳定跑通 50 局以上无报错对局
- 所有基础角色技能与裁决符合既定规则
- 每局都能输出结构化日志
- 每局都能生成基础 Replay
- 能支持至少两组 Agent 策略版本对比
- 能输出基础评测结果与排行榜

## 22. 测试案例设计

为了保证系统在正式开发阶段具备可验证性，建议从第一版开始建立覆盖后端规则、Agent 运行时、日志链路、API 输出和前端展示的测试体系。测试目标不是只验证“能运行”，而是验证“规则正确、信息隔离正确、输出可观测、界面可消费”。

### 22.1 测试分层

建议测试体系拆分为以下五层：

- 单元测试：验证规则、状态更新、可见信息裁剪、结算逻辑
- 集成测试：验证引擎、Agent、日志、API 之间的协同
- 端到端流程测试：验证完整对局能正确推进并结束
- 前端展示测试：验证页面正确渲染对局信息与复盘内容
- 回归测试：验证规则迭代后旧能力没有退化

## 23. 关键风险与应对

### 23.1 信息泄漏风险

应对：

- 只允许 Agent 获取 `player_view`
- 不允许 Agent 直接读全局状态
- 对日志和前端视图做访问分级

### 23.2 大模型输出不稳定

应对：

- 强制 JSON 输出
- 使用 schema 校验
- 做自动重试和回退
- 引入 Scripted Agent 作为基线

### 23.3 发言阶段失控

应对：

- 限制字数与格式
- 分离内部推理和公开发言
- 控制阶段超时与轮次

### 23.4 复盘流于表面

应对：

- 复盘必须绑定事件
- 输出关键节点与因果链
- 引入替代行动分析

## 26. 结论

本项目最合理的建设路径是先搭建一个稳定、可回放、可评测的狼人杀多 Agent 对局系统，再逐步增强 Agent 能力、复盘能力和观战体验。当前优先方向选择 `评测 + 复盘` 是合理的，因为它能为后续的模型迭代、Prompt 优化和多版本对比提供统一依据。

第一版只要把 `规则引擎 + 信息隔离 + 多角色 Agent + 日志回放 + 复盘归因` 这条主链打通，就已经具备一个很强的课程项目基础。后续无论扩展前端、人机混战还是自进化循环，都会有清晰的承载底座。
